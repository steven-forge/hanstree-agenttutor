# Decisions API — AI가 정해진 선택지에서 답을 고르는 방법

확인일: 2026년 10월 1일 · 주제: OpenAI, AI 활용, API

## 한눈에 이해하기

**Decisions API는 개발자가 정해 둔 질문과 선택지에 맞춰 AI의 판단을 받는 기능입니다.** OpenAI는 글이나 이미지를 상황 정보로 주면, Luna가 콘텐츠 분류·문의 전달·에이전트의 다음 행동 선택 등에 쓸 답을 돌려준다고 소개했습니다. [OpenAI 공식 발표](https://openai.com/index/devday-2026-recap/)

예를 들어 쇼핑몰에서 고객 문의를 받았을 때, “어떻게 처리할까?”라는 질문에 **바로 안내 / 담당자에게 전달 / 추가 정보 요청** 중 하나를 고르는 모습을 떠올리면 됩니다. 이 쇼핑몰 사례는 이해를 돕기 위해 만든 예시입니다.

## API는 무엇인가요?

API는 **프로그램이 다른 프로그램에 정해진 방식으로 요청하고 결과를 받는 연결 창구**입니다. 사람이 대화창에 직접 물어보는 대신, 쇼핑몰 프로그램이 필요한 판단을 요청하고 답을 받아 다음 화면이나 작업에 활용할 수 있습니다.

일상에서는 안내 데스크와 비슷합니다. 방문 목적과 준비된 서류를 확인한 뒤 어느 창구로 보내야 할지 고르는 일입니다. 이때 선택할 창구와 분류 기준을 먼저 정해 두면 역할이 분명해집니다.

이해를 위한 가상 사례 · 실제 API 호출 아님

아래는 같은 흐름을 글로 다시 정리한 것입니다. 실제 API의 요청 형식이나 내부 구조를 나타내는 것은 아닙니다.

```text
① 상황 정보
   “배송이 어디까지 왔나요?” + 주문·배송 정보
          ↓
② 질문과 선택지
   질문: 이 문의를 어떻게 처리할까?
   선택지: 바로 안내 / 담당자 전달 / 추가 정보 요청
          ↓
③ 판단 결과
   예: 바로 안내
          ↓
④ 우리 서비스의 처리
   주문 조회 권한과 배송 정보를 확인한 뒤 고객에게 안내
```

여기서 **선택 결과를 받는 단계와 실제 일을 실행하는 단계를 구분**하면 이해하기 쉽습니다. “담당자 전달”이라는 결과를 받았다면, 담당자를 정하고 문의를 보내는 일은 서비스가 구현해야 합니다.

## 상황이 바뀌면 결과는 어떻게 달라질까요?

다음은 미리 정한 기준으로 구성한 학습용 사례입니다. 실제 API를 호출해 얻은 결과가 아닙니다.

| 고객 문의와 상황 | 예시 선택 결과 | 그렇게 정한 이유 |
| --- | --- | --- |
| 배송 위치를 묻고, 조회 가능한 주문·배송 정보가 있음 | 바로 안내 | 안내에 필요한 정보가 준비되어 있음 |
| 환불을 요청함 | 담당자 전달 | 이 예시에서는 환불 검토를 담당자가 맡는다고 정함 |
| 배송 위치를 묻지만, 어떤 주문인지 알 수 없음 | 추가 정보 요청 | 주문을 먼저 알아야 배송을 안내할 수 있음 |

첫 번째 문의에서 주문 정보를 빼면 세 번째 상황이 됩니다. **질문이 같아도 주어진 정보가 다르면 적절한 선택이 달라질 수 있습니다.** 환불을 항상 사람이 맡는다는 기준도 이 예시의 운영 규칙이며, Decisions API 자체의 규칙은 아닙니다.

## 질문과 선택지를 정하는 요령

- **한 번에 한 가지를 묻습니다.** “이 고객을 모두 처리해 줘”보다 “이 문의를 어느 처리 경로로 보낼까?”처럼 범위를 좁힙니다.
- **선택지의 뜻이 겹치지 않게 정합니다.** “처리”와 “대응”처럼 비슷한 말보다 실제 다음 행동을 구분합니다.
- **정보가 부족한 경우도 준비합니다.** 필요한 정보가 없을 때 무리하게 결론을 내리지 않도록 “추가 정보 요청” 같은 경로를 설계합니다.

이 세 가지는 이 문서의 설계 제안이며, OpenAI가 발표한 필수 매개변수나 보장 사항은 아닙니다.

## 헷갈리기 쉬운 점

**선택지가 정해져 있어도 판단은 틀릴 수 있습니다.** 결과의 형태를 제한하는 것과 내용이 항상 맞는 것은 다릅니다. 서비스에 적용할 때는 실제 문의 사례로 적절한 결과인지 살펴봐야 합니다.

**선택 결과가 실행 권한을 대신하지는 않습니다.** 예를 들어 “환불 검토”를 골랐다는 이유만으로 돈이 자동으로 반환되는 것은 아닙니다. 서비스의 권한 확인과 처리 규칙이 별도로 필요합니다.

**모든 질문에 선택형 답이 어울리는 것은 아닙니다.** 글쓰기나 열린 아이디어 탐색처럼 답의 범위를 미리 정하기 어려운 작업은 다른 대화·생성 방식과 함께 생각할 수 있습니다.

## Jev와 비교하기

Decisions API와 Jev는 둘 다 프로그램이 미리 정한 틀에 맞춰 AI의 판단을 받는 데 쓰입니다. 다만 만든 곳과, API 제품과 모델이라는 구분, 공개 문서에서 확인할 수 있는 정보의 범위가 다릅니다. 아래 비교는 공개된 발표·문서를 바탕으로 쉽게 정리한 것이며, 같은 사례로 직접 비교해 정확도나 속도의 우열을 가린 결과가 아닙니다.

| 비교 항목 | Decisions API | Jev |
| --- | --- | --- |
| 무엇인가 | OpenAI가 제공하는 API 제품(기반 모델 Luna) | TypeSafe가 만든 System One 모델, API로 이용 |
| 입력 | 글 또는 이미지로 된 상황 정보 | 문서상 텍스트 또는 구조화한 state(이미지 지원 여부는 이번 자료로 확인 못 함) |
| 출력 | 정해 둔 질문에 대한 사전 정의된 답 | Choice·Noul·Score 같은 확률 기반 값 |
| 확인한 자료 | 공식 발표 중심이며, 이번 자료로 상세 규격은 확인 못 함 | 공개된 API·SDK 문서에서 형식을 확인함 |
| 선택 기준 | 같은 실제 사례로 정확도·응답 시간·비용을 직접 비교해야 함 | 직접 비교 결과 없음 · 이 문서는 승자를 정하지 않음 |

Jev 공식 문서에는 세 가지 질문 형식이 있습니다. 아래 질문은 이해를 위한 예시입니다. **Choice**는 여러 처리 경로 중 하나를 고르는 값으로, 선택 결과와 선택지별 확률을 반환합니다(예: 이 문의를 어느 경로로 보낼까). 여러 질문 형식을 한 요청에 함께 보낼 수 있습니다. **Noul**은 어떤 조건에 해당하는지를 확률로 나타낸 값(예: 환불 문의인가), **Score**는 순서가 있는 단계 중 어디에 해당하는지를 확률로 가중한 값(예: 긴급도가 어느 단계인가)입니다. 세 형태 모두 확률에서 나온 값이며 정답을 보장하지 않습니다. Decisions API와 Jev 둘 다, 판단 결과를 받은 뒤 실제로 무엇을 할지는 앱이 자신의 실행 권한과 정책을 확인해 정합니다.
