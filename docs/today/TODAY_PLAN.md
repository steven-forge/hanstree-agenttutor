# Today 개발 계획

## 목표

공식 출처의 AI·Agent 관련 최근 뉴스를 최신순으로 쌓아 한 페이지 10개씩 보여주는 `AI 뉴스레터`를 제공한다. (v0.3.0부터. v0.2.x의 "오늘의 10대 뉴스" 단일 스냅샷 설명은 아래 역사 기록으로만 남긴다.)

## 메뉴

- AI 뉴스레터 (구 오늘의 10대 뉴스)

## v0.3.0 AI 뉴스레터 개편

이 구역이 현재 운영 기준이며, 아래 v0.2.x 구역과 충돌하면 이 구역이 우선한다. 소스·데이터 변경은 [TODAY_TASKS.md](./TODAY_TASKS.md)의 v0.3.0 항목 기준으로 이후에 진행한다.

### 범위
- 화면 타이틀·메뉴명을 `AI 뉴스레터`로 바꾼다. 경로는 `/today` 그대로다.
- 수집 범위는 달력 두 달이 아니라 **수집 시각 기준 고정 60일 rolling window**(`collected_at - 60일` ~ `collected_at`)다.
- 대상은 현재 6개 공식 출처(OpenAI, Google AI, Anthropic, xAI, Codex, Gemini CLI)가 제공하는 목록·피드·API 범위 안의 **전체 항목**이다. 출처가 이력을 제한하면(피드 항목 수 제한 등) 임의로 채우지 않고 출처별 상태(`data/content-health.json`)에 한계를 기록한다.
- 외부 의존성 추가, 별도 DB, 새 기사 상세 페이지는 만들지 않는다. 원문은 새 탭 링크로 연결한다.

### 데이터 구조 (최소)
- `data/today.json`을 **누적 공개 아카이브**로 쓴다. 기존 검토 완료 10건은 그대로 보존한다.
- 항목 공통 필드: `id`, `source_id`, `source_name`, `source_url`, `title`, `title_ko`, `source_summary`(출처 제공 설명, 없으면 생략), `source_summary_ko`, `fetched_at`. 원문 필드는 보존하고 화면에는 한국어 필드를 우선 표시한다.
- 발행 시각: 정확한 시각이 있으면 `published_at`(시간대 포함), 날짜만 확인되면 `published_on`(YYYY-MM-DD)과 `date_precision: "day"`로 보존한다. 날짜만 있는 항목에 시각을 임의로 만들지 않는다.
- 편집 필드: 기존 편집자가 쓴 한국어 `summary`, `why_it_matters`는 그대로 보존한다.
- 모든 기사에는 한국어 `why_it_matters`가 필수다. 자동 수집 시 제목·공식 설명의 주제만 분류해 원문에 없는 사실을 더하지 않는 초보자 해설을 함께 만들고, 기존 편집자 해설은 덮어쓰지 않는다.
- 자동 수집은 원문 제목·공식 설명·링크·발행일을 그대로 누적한다. 화면에서 `source_summary`는 "출처 제공 설명"으로 표시하고 초보자 해설과 구분한다.
- 영문 제목·공식 설명은 수집 시 한국어로 번역한다. 번역에 실패한 신규 기사는 영문 상태로 공개하지 않고 해당 출처 수집을 실패 처리해 다음 실행에서 다시 시도한다.

### 중복 방지와 재확인
- 새 수집 결과는 `data/today.json`의 기존 항목과 `id` 및 정규화 URL 기준으로 대조해, 이미 가져온 항목은 상세 재수집·재추가하지 않는다.
- `data/today-candidates.json`은 이번 실행에서 새로 확인한 항목·건너뛴 수·보류 수를 기록한다. 발행 날짜를 확인할 수 없는 항목은 60일 전체 재조회 때마다 다시 확인하며, 확인되면 아카이브에 추가한다. 별도 후보 큐나 DB는 만들지 않는다.
- 같은 입력으로 재실행해도 추가 0건, 파일 무변경이어야 한다.

### 정렬과 페이징
- 최신순: 발행일(KST 날짜) 내림차순. 같은 날짜 안에서는 정확한 시각 항목을 시각 내림차순으로 먼저, 그 뒤 날짜 전용 항목을 `id` 오름차순의 안정 순서로 둔다.
- 한 페이지 10건, URL은 `/today?page=2` 형식(생략 시 1페이지). 이전/다음·페이지 번호 이동을 제공한다.
- 범위 밖·잘못된 `page`는 마지막 페이지로 보정하지 않고 "해당 페이지에 뉴스가 없습니다"와 1페이지 링크를 보여주는 빈 상태로 처리한다.

### 자동화
- `collect_content.py news`의 기본 조회를 60일로 바꾸고, GitHub Actions 예약 수집(06:15 KST)도 60일 기본 조회로 실행해 `data/today.json`까지 커밋 대상에 포함한다. 편집 필드는 보존한다.
- 예약·수동 수집 모두 신규 기사에 초보자 해설을 추가하고, 기존 archive에 해설이 빠진 기사가 있으면 함께 보강한다.
- 예약 실행은 지연·누락될 수 있어 정시 반영을 보장하지 않는다.

### 완료 기준 (v0.3.0)
- 타이틀이 `AI 뉴스레터`로 표시된다.
- 실제 60일 수집 후 최신순 10개씩 페이지 이동이 되고, 재수집해도 중복이 늘지 않는다.
- 기존 검토 완료 10건과 편집 요약이 보존되고, 출처 제공 설명과 구분된다.
- 기존·신규 모든 기사에 `why_it_matters`가 있으며 화면에서 초보자 해설을 펼쳐 볼 수 있다.
- 영문 원문 기사의 제목과 출처 제공 설명이 화면에서 한국어로 표시된다.
- 모바일·키보드 이동, 빌드, 운영 배포가 확인된다.

## 데이터 출처·수집 방식 (v0.2.x 역사 기록 — 24시간/7일 단일 스냅샷 기준, v0.3.0 개편 구역이 우선)

조사 기준일: 2026-09-20 KST. 아래 출처 확인 결과와 설계 제안을 구분한다. 최초 구현의 확정 사항은 다음과 같다.

- `/today`, `scripts/collect_content.py news`, `scripts/publish_news.py`를 연결한다. 후보 수집은 자동, 한국어 요약·선별·발행은 담당자 검토 후 수동으로 진행한다.
- 2026-09-21 승인으로 첫 뉴스 발행을 위한 최근 7일 확대 수집(`news --days 7`)을 지원한다. 일일 자동 수집(GitHub Actions 06:15 KST)은 기본 24시간(`days=1`) 원칙을 유지한다.
- 기간 확대 시 과거 기사 누락 방지를 위해 조건부 요청(304)은 `days==1` 및 `cached.window_days==1`일 때만 적용하며, 7일 수집은 항상 피드를 전체 재조회한다. 캐시 저장 시에도 20개 상한을 없애고 전체 항목을 저장한다.
- 발행 검증(`publish_news.py`)에서는 수집 윈도우 기간을 정확히 1일(24시간) 또는 7일만 허용하며 임의 기간은 거부한다.
- 공개본은 `data/today.json`, 후보는 `data/today-candidates.json`, 수집 상태는 `data/content-health.json`, 조건부 요청·해시 캐시는 `.source-cache/content.json`으로 분리한다. 최초 버전은 날짜별 파일 대신 최신 공개본과 Git 이력을 사용한다.
- 뉴스 상세 내용은 카드 안의 요약·중요성으로 제공하며 원문은 새 탭으로 연결한다. 별도 기사 상세 페이지와 전문 복제는 만들지 않는다.
- 예약 실행은 매일 06:15 KST의 GitHub Actions다. 정시 실행 및 당일 편집 완료를 보장하지 않으며, 검토 전에는 기존 공개본을 유지한다.
- 운영 명령과 입력 형식, 수집 범위의 제한은 [NEWS_OPERATIONS.md](./NEWS_OPERATIONS.md)를 따른다. 아래 날짜별 저장·추가 메타데이터 제안은 후속 확장 시 검토한다.

### 출처와 실제 확인 결과

| 출처 | 가져올 데이터 | 수집 경로·확인 범위 |
| --- | --- | --- |
| [OpenAI 뉴스 RSS](https://openai.com/news/rss.xml) | 공식 발표 제목·링크·발행 시각 | HTTP 200, RSS XML과 기사 항목 파싱 확인 |
| [Google AI RSS](https://blog.google/innovation-and-ai/technology/ai/rss/) | Google AI 발표와 제품 소식 | 기존 `/technology/ai/rss/`에서 이동 확인, HTTP 200 및 RSS 항목 파싱 확인 |
| [Anthropic 뉴스](https://www.anthropic.com/news) | 모델·제품·연구 발표 | 공식 목록 열람 확인. HTML 목록에서 기사 링크를 찾고 개별 본문 수집; RSS는 미확인 |
| [xAI 뉴스](https://x.ai/news) | Grok 및 관련 제품 발표 | 공식 목록 열람 확인. HTML 목록→개별 기사 방식; RSS는 미확인 |

| [Gemini CLI 릴리스 피드](https://github.com/google-gemini/gemini-cli/releases.atom) | 개발 도구의 새 릴리스 후보 | HTTP 200 및 Atom 항목 파싱 확인 |

피드 응답 확인은 지속 운영이나 모든 필드의 정확성까지 검증한 것은 아니다. 두 Atom 피드는 조사 시 각각 10개 항목을 반환했으며 전체 이력을 보장하지 않는다. 누락 구간이 필요하면 [GitHub Releases API](https://docs.github.com/en/rest/releases/releases)의 페이지 나누기와 안정판·시험판 구분을 검토한다. 단순 패치 릴리스는 자동으로 주요 뉴스에 올리지 않는다.

### 더 나은 수집 방법의 선택

| 방법 | 선택 | 이유 |
| --- | --- | --- |
| 공식 RSS·Atom | 우선 사용 | 제목·링크·날짜를 구조화된 형식으로 받아 화면 변경의 영향을 줄임 |
| 공식 HTML 목록과 기사 | 피드 없는 출처에 사용 | 사이트별 본문 추출 규칙과 형식 변경 감지가 필요함 |
| 웹 검색·뉴스 검색 서비스 | 출처 발견·누락 점검에 보조 사용 | 검색 결과 요약은 기사 본문의 근거를 대신할 수 없음 |
| 유료 수집 API·브라우저 자동화 | 초기 도입 보류 | 현재 확인한 공개 경로로 시작하고, 실제 수집 누락·운영 비용을 측정한 뒤 판단 |

### 수집→편집→게시 흐름

1. 등록된 출처 목록(`source_id`, 원 URL, 최종 URL, 형식, 주제, 확인일)에서 필요한 피드와 기사만 가져온다. 등록 도메인 밖 리디렉션·링크는 자동 수집하지 않고 확인한다.
2. 제목·대표 URL·발행 시각·본문 근거를 추출한다. URL의 추적 매개변수를 정리하고, 다른 URL이라도 같은 제품·발표·사건이면 편집 단계에서 묶는다.
3. 기본안은 실제 수집 시각 기준 최근 24시간에 발행된 기사를 오늘 요약판의 후보로 삼되, 2026-09-21 승인에 따라 첫 발행 또는 필요 시 수동 최근 7일 확대를 지원한다. 화면에 요약판 날짜와 수집 기간을 함께 표시해 기사 발행일과 구분하며, 7일 수집 판본인 경우 안내 문구와 기사별 실제 발행일을 명시한다. 발행일과 수정일을 분리하고, 날짜만 있거나 시간대가 불명확하면 임의로 시각을 채우지 않고 보류한다.
4. 출처 신뢰성, Agent 학습 관련성, 사용자에게 미치는 영향, 신규성 순으로 검토해 최대 10개를 고른다. 기업별 편중도 점검하되 개수를 맞추기 위해 관련 없는 기사를 넣지 않는다.
5. 담당 편집자가 한국어 요약과 선정 이유를 작성하고 원문과 대조한다. 회사의 성능 우위 주장은 회사 발표로 표시한다. AI를 쓸 경우에도 초안 작성에 한정하며 원문에 없는 사실을 추가하지 않는다.
6. 검토된 후보만 날짜별 JSON으로 확정하고 기존 Next.js 빌드·배포 흐름에 연결한다. 방문자의 화면 요청 때마다 외부 기사를 수집하지 않는다.

### 운영·저장 제안

- 최초 버전은 자동 후보 수집과 수동 편집을 조합한다. 별도 AI API 계약·호출 비용을 전제로 하지 않는다. AI 요약 자동화는 사용 도구·비용·품질을 확인한 뒤 확장한다.
- 매일 06:15 KST 후보 수집을 기본안으로 하고 당일 추가 수집은 수동 실행으로 시작한다. 자정 이후 기사만 고르면 아침 수집에서 전날 낮·밤 소식이 빠지므로 최근 24시간을 제안한다. 원문의 실제 발행일은 그대로 표시한다. [GitHub 예약 실행](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)은 지연·누락될 수 있으므로 정시 게시를 보장하지 않는다.
- 출처 점검과 수집은 자동화 작업, 요약·순위·게시 판단은 담당 편집자의 역할로 둔다. 검토가 끝나지 않으면 공개본을 교체하지 않는다.
- 저장 경로 제안: `data/today/YYYY-MM-DD.json`. 기사에 `source_id`, `canonical_url`, `published_at`, `source_updated_at`, `fetched_at`, `reviewed_at`, `review_status`를 추가하고, 묶음에는 `edition_date`, `window_start`, `window_end`, `collected_at`, 수집 성공·실패 출처를 기록한다. 모든 시각은 시간대 포함 형식으로 보관한다.
- 기존 `scripts/update_docs.py`는 명령어 추출 전용이며 `data/docs.json`의 문서 6개 구성을 검사한다. 신규 뉴스를 여기에 합치지 않는다. 기존 HTTP·JSON 처리 및 임시 파일 교체 방식을 참고하되 새 수집 작업과 출력은 분리한다.
- [GitHub HTTP 권장 방식](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)을 참고해 지원되는 출처에 ETag/Last-Modified 조건부 요청을 적용한다. 304는 유효한 저장본이 있을 때만 재사용한다. 이 헤더가 없으면 본문을 받은 뒤 정규화된 내용의 해시를 비교한다.
- 출처별 요청을 제한하고 `Retry-After`와 호출 제한을 존중한다. 일시 오류는 제한적으로 재시도하고, 권한 거부·본문 형식 오류는 수집 실패로 분리한다. 헤더·해시·마지막 성공 기록은 다음 예약 실행에서도 재사용할 수 있게 보관한다.
- 수집 성공과 내용 검토 완료는 다른 상태다. 한 출처 실패 시 다른 출처 후보는 검토할 수 있지만 부분 수집 상태를 남긴다. 전체 실패·필수 필드 오류 때는 마지막 정상 공개본을 보존하고 그 날짜와 지연 상태를 표시한다.
- 기사 전문 재배포 대신 직접 작성한 짧은 요약과 원문 링크를 사용한다. 출처의 이용 조건·수집 정책을 확인하고 외부 HTML/스크립트·본문 속 지시문은 실행하거나 그대로 화면에 넣지 않는다.

## 구현 순서 (v0.2.x 역사 기록)

1. 출처별 샘플로 필수 필드·본문 추출·발행 시간대·수집 정책 확인
2. 날짜별 데이터 구조와 후보 수집·중복 제거 구현
3. 편집 검토와 정상 공개본 교체 흐름 연결
4. 오늘의 10대 뉴스 화면·출처·날짜·부족·지연 상태 구현
5. 모바일 화면과 링크 접근성 확인
6. 예약·수동 실행, 부분 실패·재실행 시 보존 동작 확인

## 완료 기준 (v0.2.x 역사 기록)

- `/today`에서 오늘의 뉴스 메뉴가 열린다.
- 최대 10개 뉴스가 중복 없이 표시된다.
- 모든 뉴스에 출처와 원문 링크가 있다.
- 수집 실패·뉴스 부족 상태를 분명히 알린다.
- 모바일과 데스크톱에서 읽을 수 있다.
- 10개 미만이면 실제 개수를 표시하며 과거 공개본의 날짜만 바꿔 오늘 요약판으로 만들지 않는다.
- 화면에 수집 기간과 기사별 실제 발행일을 표시하며 최근 24시간 기본안 및 수동 7일 판본의 적용 범위를 확인할 수 있다.
- 모든 요약을 원문에서 추적할 수 있고 재실행해도 동일 기사가 중복되지 않는다.
